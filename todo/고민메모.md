# 고민 메모 (racingcar)

## 1. 랜덤값 테스트
- 진짜 `Random`은 값 예측 불가 → 테스트 더블로 고정값 주입
- `RandomGenerator` 상속해 `generateNumber()`가 고정값 반환
- 경계값으로 검증: `MOVE_THRESHOLD`(전진), `MOVE_THRESHOLD - 1`(정지)

## 2. assert에서 getter 체이닝
- `car.getPosition().getPosition()`은 디미터 법칙 위반(내부 2겹 노출)
- Position은 값 객체 → `equals`/`hashCode` 구현 후 `isEqualTo(new Position(1))`
- equals만 재정의하면 안 됨: 규약상 hashCode도 같이 (HashSet/HashMap에서 깨짐)

## 3. private 메서드 테스트 고민 (핵심)
- "테스트 위해 private→public 여는 게 아쉽다"는 **설계 신호**
- 접근제어자를 바꾸는 게 아니라, **로직이 제자리에 없는 것**
- `createCars`는 도메인 규칙인데 Application(main)에 박혀 있음 → 도메인으로 이동

## 4. 일급 컬렉션
- 정의: 인스턴스 필드가 **컬렉션 딱 하나뿐**인 클래스
- `RacingCar`는 `cars` + `attemptCount` 2개 필드 → 일급 컬렉션 아님
- `Cars`로 분리 (필드는 `List<Car>` 하나) → RacingCar가 품어서 사용
- 효과: 생성/이동/위치수집 로직 응집, RacingCar의 for문 제거, 테스트 쉬워짐

## 5. MoveStrategy 추상화 후 테스트의 검증 단위
- 인터페이스로 추상화했는데 CarTest는 수정이 하나도 없었음 → 컴파일 안 깨진 건 추상화 성공(OCP) 신호
- 근데 "4 이상"이라는 규칙 자체를 Car는 모름 (Car가 아는 건 `movable()`의 true/false뿐)
- 그래서 `랜덤_값이_4_이상이면_위치가_1_증가한다`는 Car의 테스트가 아니라 RandomMoveStrategy의 규칙을 Car 경유로 검증하는 것
- 분리 방향:
  - CarTest: "움직일 수 있으면 위치 1 증가" → boolean Fake(람다 `() -> true`)
  - RandomMoveStrategyTest: "4 이상이면 movable true" → 숫자 Fake(`FixedRandomGenerator`)
- 효과: 임계값이 4→5로 바뀌어도 CarTest는 안 깨짐 (각 테스트가 자기 책임만 검증)

## 6. Todo를 객체의 책임 단위로 쪼개는 게 맞나?
- 책임 분리하니 Todo 한 줄("랜덤 값이 4 이상이면 위치 1 증가")이 두 객체의 Todo로 쪼개짐
  - Car: "움직일 수 있으면 위치 1 증가" / RandomMoveStrategy: "4 이상이면 움직일 수 있다"
- 근데 읽는 사람 입장에선 쪼개기 전 문장이 더 직관적 — 요구사항이 한눈에 보임
- 쪼갠 문장은 설계(인터페이스 구조)를 알아야 이해됨 → Todo가 구현을 따라가는 느낌
- Todo와 단위 테스트는 1:1이 되기에 한계가 있음
  - Todo는 요구사항 수준에서 시작 → 리팩터링으로 책임이 갈라지면 테스트 단위는 더 잘게 내려감
- 일단 결론: 객체마다 Todo를 작성하고 있으니 Todo도 같이 분리하되, "요구사항 관점의 직관성 vs 책임 관점의 정확성" 긴장은 계속 고민
  - 객체마다의 Todo는 요구사항 관점의 직관성이 떨어질 수밖에 없음
  - 요구사항의 직관성은 단위 테스트로는 한계가 있음
  - 직관적인(요구사항 수준의) Todo는 통합 테스트가 맞을 수도 — "랜덤 값이 4 이상이면 위치 1 증가"는 Car+RandomMoveStrategy를 함께 묶어 검증하는 자리
